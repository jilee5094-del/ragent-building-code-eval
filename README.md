# ragent-building-code-eval

基于开源项目 [nageoffer/ragent](https://github.com/nageoffer/ragent) 搭建住宅设计规范 GB 50096-2011 知识库，并对不同检索配置做了一组对照评测。

平台本身未做代码修改，本仓库只包含数据处理脚本、评测集、评测脚本和实验结果。

## 环境

- Ragent 本地部署，依赖 PostgreSQL + pgvector 0.8、Redis 7、RocketMQ、rustfs、Elasticsearch 9.1 + IK 分词
- 模型使用阿里云百炼：qwen-plus 负责改写与意图识别，text-embedding-v4 生成 1536 维向量，qwen3-rerank 负责精排

## 知识库

GB 50096-2011 正文共 218 条，其中强制性条文 65 条，依据住建部公告第 1093 号标注。条文文本取自两个公开来源并逐条比对，两边都有的条文文字和数值完全一致，其中一个来源缺失的 6.2.1、6.2.2 两条从另一个来源补齐。

整理格式：每章一个文件，每条一个四级标题，正文开头写明规范号和条文号，例如：

```
#### 5.2.1
【GB 50096-2011 第5.2.1条】卧室的使用面积应符合下列规定：……
```

条文号写进正文而不是只放在标题里，是因为 Ragent 组装上下文时不会把文档标题和章节路径传给模型，只有写在正文里，回答才能引用到。

8 个文件分块后得到 51 个块，平均约 440 字，每块都带有条文号。另在意图树中新增规范问答节点，并在节点提示词里约束回答必须标注条文出处。

规范全文受版权保护，仓库中只保留 `samples/` 下的 10 条示例。

## 评测集

`eval/gb50096_eval.jsonl` 共 40 题：

| 题型 | 数量 | 示例 |
|---|---|---|
| 单条数值 | 12 | 入户管供水压力上限是多少 |
| 条件组合 | 8 | 不超过六层、一边有栏杆的楼梯梯段净宽最小多少 |
| 按条文号查询 | 6 | GB 50096 第 6.4.1 条规定了什么 |
| 口语化提问 | 6 | 几层楼以上的住宅一定要装电梯 |
| 一问多答 | 4 | 卧室净高最低多少，楼梯梯段净宽最低多少 |
| 规范中无答案 | 4 | 住宅小区绿地率最低是多少 |

`build_dataset.py` 生成数据集时会检查每题的答案要点是否出现在所标注条文的原文中。评测脚本调用 Ragent 自带的 `/rag/eval` 接口，只做检索不调用生成模型，从召回内容中解析条文号来计算指标。

## 结果

四组配置，每组跑 3 轮取平均，三轮之间基本没有波动。

| 指标 | A 仅向量 | B 向量 + Rerank | C 混合检索 + Rerank | D 混合检索 |
|---|---|---|---|---|
| Recall@1 | 0.625 | 0.819 | 0.819 | 0.681 |
| Recall@3 | 0.903 | 0.903 | 0.903 | 0.875 |
| Recall@5 | 0.931 | 0.903 | 0.903 | 0.875 |
| Recall@10 | 0.931 | 0.912 | 0.903 | 0.931 |
| MRR 单问题 | 0.761 | 0.876 | 0.875 | 0.788 |
| 条文号查询 Recall@5 | 0.667 | 0.667 | 0.667 | 0.333 |
| 口语化提问 Recall@5 | 1.000 | 0.833 | 0.833 | 1.000 |
| 无答案题拒答率 | 0 | 0 | 0 | 0 |
| P50 延迟 | 2.9s | 3.1s | 3.3s | 3.0s |

混合检索指向量通道加 Elasticsearch 关键词通道，经 RRF 融合。各组配置差异见 `eval/configs/`，原始结果见 `eval/results/`。

## 分析

Rerank 的主要作用是把正确条文排到第一位。A 组有 10 道题的正确条文排在第 2 到第 4 位，加上 Rerank 后基本都到了第 1 位，Recall@1 从 0.625 提升到 0.819。代价是一道口语题被排到了第 9 位，精排模型没有把"吊顶压低的局部"和规范里的"局部净高"对应起来，因此 Recall@5 略有下降。

按条文号查询在四组配置下都表现不好，其中两题在任何配置下都没进前 10。向量模型和精排模型都不理解 6.4.1 这样的编号。加入关键词通道也没有改善，原因出在数据格式上：每块包含 3 到 6 条条文，每条前都有"GB 50096-2011 第……条"，这些词在所有块里反复出现，问句里恰好也有，BM25 的得分被它们主导。直接在 ES 里只搜"6.4.1"时目标块排第一，带上整句问题后就排不进前三。为了让回答能引用条文而加的标注，反过来干扰了关键词检索。

无答案题没有一题被拒答。知识库全部是住宅规范，任何住宅相关的问题都能召回看起来相关的条文，最高精排分始终高于证据闸门的默认阈值 0.2。

C 组与 B 组结果一致。日志显示关键词通道确实召回了 15 条结果并进入了候选池，但最终排序由 Rerank 决定，关键词通道的贡献被覆盖了。

## 后续可做

- 检索前用正则识别问句中的条文号，命中时对该条文做精确匹配并提高权重
- 建关键词索引时去掉重复的规范号前缀，或者单独建一个条文号字段
- 用评测集的精排分分布重新确定闸门阈值
- 加入 GB 50016 建筑设计防火规范，并标注已被 GB 55037-2022 替代的条文

## 部署中遇到的问题

- Ragent 仓库自带的 ES 启动脚本使用 8.17 版本，而依赖的 elasticsearch-java 客户端是 9.4.2，版本不兼容导致启动失败，换成 ES 9.1 后正常
- 知识库是逻辑删除，collection 名称又有唯一约束，删除后无法用原名重建，评测时改为带时间戳的名称
- 文档上传接口需要 processMode 参数，缺少时直接报错
- Spring Boot 会读取工作目录下的 application.yaml，启动 mcp-server 时如果工作目录不对，会误读主服务配置导致端口冲突

## 目录

| 路径 | 内容 |
|---|---|
| `scripts/ingest_gb_codes.py` | 创建知识库、上传并分块、创建意图节点，只调用 Ragent 已有接口 |
| `eval/build_dataset.py` | 生成评测集并校验答案出处 |
| `eval/run_eval.py` | 运行评测，计算 Recall@K、Hit@K、MRR、拒答率和延迟 |
| `eval/results/` | 四组实验原始结果与失败案例 |
| `eval/configs/` | 四组实验的配置差异 |
| `samples/` | 示例条文 |
